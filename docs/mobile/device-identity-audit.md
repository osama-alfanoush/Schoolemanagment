# Device identity audit: `PushToken` versus `DeviceToken`

## Executive conclusion

Keep `DeviceToken` and retire `PushToken` through a separately reviewed data migration. `DeviceToken` is the later, richer registry; it is wired into notification preferences, delivery tracking, invalid-token cleanup, authenticated device-management endpoints, the React API client, and feature tests (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:68`, `laravel-api/app/Services/NotificationService.php:179`, `laravel-api/app/Services/NotificationService.php:213`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:143`, `school-web/src/lib/api.ts:1014`, `laravel-api/tests/Feature/NotificationTest.php:157`).

`PushToken` is not dead code: the authenticated legacy registration endpoint writes it, and the still-called `Notifier` service reads it and sends FCM requests (`laravel-api/routes/api.php:66`, `laravel-api/app/Http/Controllers/Api/AuthController.php:431`, `laravel-api/app/Services/Notifier.php:41`, `laravel-api/app/Services/AssignmentService.php:32`). `DeviceToken` is also not dead code: enhanced registration/list/removal routes use it, and the enhanced notification sender reads it (`laravel-api/routes/api.php:99`, `laravel-api/routes/api.php:101`, `laravel-api/app/Services/NotificationService.php:215`). The production code therefore contains two runtime-reachable push stacks.

## 1. Model definitions

### `PushToken`

- **Table and model:** Eloquent model `App\Models\PushToken`; its schema table is `push_tokens` (`laravel-api/app/Models/PushToken.php:7`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`).
- **Columns:** `id`; `user_id` foreign key to `users` with cascade-on-delete; string `token`; string `platform`; `created_at`; and `updated_at` (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:279`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:283`). The mass-assignable fields are `user_id`, `token`, and `platform` (`laravel-api/app/Models/PushToken.php:9`).
- **Indexes and constraints:** the migration declares a unique composite constraint on `(user_id, token)` in addition to the user foreign key; it declares no globally unique constraint on `token` (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:280`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:284`).
- **Relationships:** `PushToken` declares no relationship method itself, while `User::pushTokens()` declares the inverse `hasMany(PushToken::class)` relationship (`laravel-api/app/Models/PushToken.php:7`, `laravel-api/app/Models/PushToken.php:10`, `laravel-api/app/Models/User.php:152`, `laravel-api/app/Models/User.php:155`).
- **School/tenant scope:** the row has `user_id` but no `school_id`, so it is user-scoped rather than school-row-scoped (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:285`). The tenancy configuration states that configured tenant models must have a non-null `school_id`, which this schema cannot satisfy (`laravel-api/config/tenancy.php:89`, `laravel-api/config/tenancy.php:91`).

### `DeviceToken`

- **Table and model:** Eloquent model `App\Models\DeviceToken`; its schema table is `device_tokens` (`laravel-api/app/Models/DeviceToken.php:9`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:69`).
- **Columns:** `id`; `user_id` foreign key to `users` with cascade-on-delete; indexed string `token`; string `platform`; nullable strings `device_name` and `app_version`; nullable timestamps `last_used_at` and `verified_at`; `created_at`; and `updated_at` (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:70`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:78`). The model makes those device fields mass assignable and casts `last_used_at` and `verified_at` to datetimes (`laravel-api/app/Models/DeviceToken.php:13`, `laravel-api/app/Models/DeviceToken.php:21`).
- **Indexes and constraints:** the migration declares an index on `token`, a unique composite constraint on `(user_id, token)`, and the user foreign key; it does not make `token` globally unique (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:71`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:79`).
- **Relationships:** `DeviceToken::user()` is a `belongsTo(User::class)` relationship; `User` has no corresponding `deviceTokens()` relationship in the inspected token references (`laravel-api/app/Models/DeviceToken.php:29`, `laravel-api/app/Models/DeviceToken.php:32`, `laravel-api/app/Models/User.php:152`).
- **School/tenant scope:** like `PushToken`, it has `user_id` but no `school_id`, so it is user-scoped rather than school-row-scoped (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:69`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:80`). A user can have multiple school-role rows, so a single user's device registry can span school contexts (`laravel-api/app/Models/User.php:78`, `laravel-api/app/Models/User.php:80`).

### Related identity and notification models

`TokenIssuer` is auth-token issuance, not a push-device registry: it creates access/refresh or limited Sanctum tokens and stores a `device_name` and token family, but it does not read or write either push-token model (`laravel-api/app/Services/TokenIssuer.php:5`, `laravel-api/app/Services/TokenIssuer.php:11`, `laravel-api/app/Services/TokenIssuer.php:20`, `laravel-api/app/Services/TokenIssuer.php:30`). `AuthController` injects `TokenIssuer`, while its push registration method separately calls `PushToken::updateOrCreate`; there is no database relationship between those records (`laravel-api/app/Http/Controllers/Api/AuthController.php:29`, `laravel-api/app/Http/Controllers/Api/AuthController.php:30`, `laravel-api/app/Http/Controllers/Api/AuthController.php:431`, `laravel-api/app/Http/Controllers/Api/AuthController.php:440`).

`NotificationPreference` is a per-user channel/type policy that can create defaults and suppress push during quiet hours (`laravel-api/app/Models/NotificationPreference.php:31`, `laravel-api/app/Models/NotificationPreference.php:40`, `laravel-api/app/Models/NotificationPreference.php:61`, `laravel-api/app/Models/NotificationPreference.php:88`). `NotificationDelivery` records channel status and timestamps and belongs to a notification (`laravel-api/app/Models/NotificationDelivery.php:13`, `laravel-api/app/Models/NotificationDelivery.php:22`, `laravel-api/app/Models/NotificationDelivery.php:44`, `laravel-api/app/Models/NotificationDelivery.php:46`). `Notification` exposes the inverse `deliveries()` relationship (`laravel-api/app/Models/Notification.php:88`, `laravel-api/app/Models/Notification.php:90`).

## 3. Live notification send paths and dead-code assessment

There are two live code paths:

1. The legacy path is caller -> `Notifier::send()` -> create `AppNotification` -> `Notifier::dispatchPush()` -> `PushToken` lookup -> FCM (`laravel-api/app/Services/Notifier.php:17`, `laravel-api/app/Services/Notifier.php:28`, `laravel-api/app/Services/Notifier.php:36`, `laravel-api/app/Services/Notifier.php:48`, `laravel-api/app/Services/Notifier.php:57`). Production callers include assignment creation and grading (`laravel-api/app/Services/AssignmentService.php:32`, `laravel-api/app/Services/AssignmentService.php:71`).
2. The enhanced path is caller -> `NotificationService::sendWithTemplate()`/`sendToMany()` -> `send()` -> preference checks -> `deliverPush()` -> `DeviceToken` lookup -> `NotificationDelivery` -> FCM, with invalid-token cleanup (`laravel-api/app/Services/NotificationService.php:23`, `laravel-api/app/Services/NotificationService.php:56`, `laravel-api/app/Services/NotificationService.php:129`, `laravel-api/app/Services/NotificationService.php:179`, `laravel-api/app/Services/NotificationService.php:215`, `laravel-api/app/Services/NotificationService.php:221`, `laravel-api/app/Services/NotificationService.php:252`, `laravel-api/app/Services/NotificationService.php:295`). Production callers include budget overruns and goods-received events (`laravel-api/app/Services/BudgetService.php:101`, `laravel-api/app/Services/BudgetService.php:107`, `laravel-api/app/Listeners/NotifyGoodsReceived.php:17`, `laravel-api/app/Listeners/NotifyGoodsReceived.php:25`).

Neither model is dead code because each has a reachable authenticated writer and a production sender that reads it (`laravel-api/routes/api.php:66`, `laravel-api/routes/api.php:99`, `laravel-api/app/Services/Notifier.php:48`, `laravel-api/app/Services/NotificationService.php:215`). Actual external push transmission in either path remains configuration-dependent: legacy returns when the FCM server key is absent, while enhanced delivery also checks the integration gate (`laravel-api/app/Services/Notifier.php:43`, `laravel-api/app/Services/Notifier.php:46`, `laravel-api/app/Services/NotificationService.php:237`, `laravel-api/app/Services/NotificationService.php:246`).

## 4. Migration history

`push_tokens` came first in migration `2026_04_17_100000_create_school_schema.php` (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`). Ten days later, migration `2026_04_27_000001_create_enhanced_notifications_schema.php` introduced `device_tokens` under the comment “Push tokens with better tracking,” alongside preferences and delivery logs (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:43`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:68`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:82`).

The later migration signals an intended semantic successor, but it did not supersede `push_tokens` operationally: its `up()` creates `device_tokens` without renaming, copying, or dropping `push_tokens`, and its `down()` drops only the enhanced tables (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:69`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:80`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:128`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:136`). The original migration still independently drops `push_tokens` in its rollback (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:341`).

## 5. IDOR and tenant-isolation exposure

The direct device endpoints do not expose a conventional row-ID IDOR. All routes sit in a group requiring Sanctum authentication, active account, usable access token, changed password, and school context (`laravel-api/routes/api.php:60`). `PushToken` registration derives `user_id` from the authenticated user and accepts only token/platform input (`laravel-api/app/Http/Controllers/Api/AuthController.php:431`, `laravel-api/app/Http/Controllers/Api/AuthController.php:439`). `DeviceToken` registration, deletion, and listing likewise force `$request->user()->id`; clients cannot submit another `user_id` or select a device-row ID (`laravel-api/app/Http/Controllers/Api/NotificationController.php:146`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:163`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:174`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:190`). Therefore, through these endpoints, one user cannot read, overwrite, or delete another user's device row (`laravel-api/app/Models/DeviceToken.php:50`, `laravel-api/app/Models/DeviceToken.php:52`).

Neither registry can enforce ownership by school because neither row stores `school_id` (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:69`). Both senders first verify that the recipient user belongs to the current school, but both then fetch all tokens for that user without a school predicate (`laravel-api/app/Services/Notifier.php:19`, `laravel-api/app/Services/Notifier.php:26`, `laravel-api/app/Services/Notifier.php:48`, `laravel-api/app/Services/NotificationService.php:142`, `laravel-api/app/Services/NotificationService.php:149`, `laravel-api/app/Services/NotificationService.php:215`). Thus another user or an unrelated school's user cannot address the row through the exposed APIs, but a single account used in multiple schools has one global device registry visible and usable from each authorized school context (`laravel-api/app/Models/User.php:78`, `laravel-api/app/Models/User.php:80`).

Both schemas permit the same raw token to be associated with multiple users because uniqueness is `(user_id, token)`, not `token` alone (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:284`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:72`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:79`). This is not a row-ID IDOR, but it is a device-binding integrity risk to resolve when consolidating the registry, because registration accepts any token string presented by the authenticated client (`laravel-api/app/Http/Controllers/Api/AuthController.php:433`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:148`).

## 7. Migration options

### Option A — keep `PushToken`

- **Rows affected:** every current `device_tokens` row must be copied or reconciled into `push_tokens`; the count and overlap with existing `(user_id, token)` rows are unknown without current database access (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:69`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:79`). Preserving enhanced behavior also requires retaining or adding `device_name`, `app_version`, `last_used_at`, and `verified_at`, because `push_tokens` lacks them and enhanced sending excludes unverified rows (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:285`, `laravel-api/app/Models/DeviceToken.php:55`, `laravel-api/app/Models/DeviceToken.php:63`).
- **Code sites that would change:** adapt or replace the richer helpers currently in `DeviceToken` (`laravel-api/app/Models/DeviceToken.php:34`, `laravel-api/app/Models/DeviceToken.php:69`); change device registration/removal/listing in `NotificationController` (`laravel-api/app/Http/Controllers/Api/NotificationController.php:155`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:188`); change lookup and invalid-token cleanup in `NotificationService` (`laravel-api/app/Services/NotificationService.php:215`, `laravel-api/app/Services/NotificationService.php:295`); and update feature-test table expectations and fixtures (`laravel-api/tests/Feature/NotificationTest.php:172`, `laravel-api/tests/Feature/NotificationTest.php:182`, `laravel-api/tests/Feature/NotificationTest.php:196`). The public enhanced endpoint shapes can remain stable because the React client calls routes rather than model/table names (`school-web/src/lib/api.ts:1014`, `school-web/src/lib/api.ts:1018`).
- **Rollback plan:** before cutover, snapshot both tables; retain `device_tokens` until verification; on rollback, restore it from the snapshot or reverse-copy the common fields plus preserved metadata, then restore the controller/service model targets (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:70`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:79`).
- **Risk:** **high**. This direction moves the enhanced path onto the poorer schema and can silently disable push if `verified_at` semantics are lost; it also requires changing the tested enhanced controller/service path (`laravel-api/app/Models/DeviceToken.php:57`, `laravel-api/app/Services/NotificationService.php:215`, `laravel-api/tests/Feature/NotificationTest.php:157`).

### Option B — keep `DeviceToken`

- **Rows affected:** every current `push_tokens` row must be copied or reconciled into `device_tokens`; the count and overlap with existing `(user_id, token)` rows are unknown without current database access (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:278`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:284`). A cutover must explicitly choose `verified_at` for migrated rows because the source has no verification column and the enhanced read path ignores null `verified_at` (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:279`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:285`, `laravel-api/app/Models/DeviceToken.php:57`).
- **Code sites that would change:** point `AuthController::registerPushToken()` at the canonical `DeviceToken::register()` or retire that duplicate endpoint after client migration (`laravel-api/app/Http/Controllers/Api/AuthController.php:431`, `laravel-api/app/Http/Controllers/Api/AuthController.php:440`, `laravel-api/app/Models/DeviceToken.php:34`); retarget or remove `User::pushTokens()` (`laravel-api/app/Models/User.php:152`, `laravel-api/app/Models/User.php:155`); and route legacy `Notifier` through `NotificationService` or make it read the canonical verified registry (`laravel-api/app/Services/Notifier.php:17`, `laravel-api/app/Services/Notifier.php:48`, `laravel-api/app/Services/NotificationService.php:129`, `laravel-api/app/Services/NotificationService.php:215`). Existing enhanced routes, React methods, and device tests already target the retained implementation (`laravel-api/routes/api.php:99`, `school-web/src/lib/api.ts:1014`, `laravel-api/tests/Feature/NotificationTest.php:157`).
- **Rollback plan:** before cutover, snapshot both tables; retain `push_tokens` through a verification window; on rollback, reverse-copy `user_id`, `token`, and `platform` from the canonical rows, then restore `AuthController` and `Notifier` to their present targets (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:279`, `laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:284`, `laravel-api/app/Http/Controllers/Api/AuthController.php:437`, `laravel-api/app/Services/Notifier.php:48`).
- **Risk:** **medium**, primarily around unknown production rows, overlap resolution, and assigning verification state to legacy registrations; the destination already supports the metadata, preference-aware sender, delivery audit, and invalid-token cleanup required by the enhanced path (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:72`, `laravel-api/app/Services/NotificationService.php:179`, `laravel-api/app/Services/NotificationService.php:221`, `laravel-api/app/Services/NotificationService.php:291`).

## 8. Recommendation

Choose **Option B: keep `DeviceToken`**. It is the later “better tracking” design, has explicit device metadata and verification state, supports user-facing registration/removal/listing, participates in preference-aware delivery, records delivery outcomes, removes invalid registrations, and has feature-test coverage (`laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:68`, `laravel-api/app/Models/DeviceToken.php:13`, `laravel-api/app/Http/Controllers/Api/NotificationController.php:143`, `laravel-api/app/Services/NotificationService.php:174`, `laravel-api/app/Services/NotificationService.php:221`, `laravel-api/app/Services/NotificationService.php:291`, `laravel-api/tests/Feature/NotificationTest.php:157`).

Do not drop or bulk-delete either table until current production counts, duplicate `(user_id, token)` overlap, cross-user token reuse, and the desired `verified_at` backfill rule have been measured against a current database; the schemas' uniqueness rules and the enhanced verified-token filter make those decisions data-sensitive (`laravel-api/database/migrations/2026_04_17_100000_create_school_schema.php:284`, `laravel-api/database/migrations/2026_04_27_000001_create_enhanced_notifications_schema.php:79`, `laravel-api/app/Models/DeviceToken.php:57`). During a future cutover, preserve the existing authenticated routes until clients are migrated, consolidate both `Notifier` and `NotificationService` behind the canonical registry, and add explicit cross-user/cross-school device-isolation tests before retiring `PushToken` (`laravel-api/routes/api.php:60`, `laravel-api/routes/api.php:66`, `laravel-api/routes/api.php:99`, `laravel-api/app/Services/Notifier.php:48`, `laravel-api/app/Services/NotificationService.php:215`).
