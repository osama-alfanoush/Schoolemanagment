School Management Suite

7.0 Overall / 10

This is a serious, professionally-built application, not a prototype dressed as one. The domain modelling is genuinely sophisticated — double-entry accounting with idempotency keys, maker–checker approval chains, refresh-token rotation with reuse detection, and row-level locking on every financial mutation. Three claims in the repository's own readiness report do not hold

  • “Reads and writes on school models fail outside CurrentSchool.” — They do not fail. Unscoped reads silently return every tenant's rows (SEC-2).
  • “A closed or audited period prevents creating an entry.” — audited periods still accept manual entries (LOG-2).

These are drift and over-claiming rather than dishonesty — but a readiness document that overstates its guarantees is itself a production risk, because the next engineer will trust it.

Section 02 · 7.5 / 10

Logic and correctness

The business logic is the most impressive part of this codebase. It models things most school systems get wrong: financial periods that lock, approval chains that prevent self-authorisation, and monetary calculations done in integer minor units rather than floats.

What earns the score

  • Real double-entry accounting. JournalBatchService rejects any batch where debits ≠ credits, computed in integer cents to avoid float drift.
  • Idempotency throughout. Ledger postings key on school:{id}:{source}:{sourceId}, so a retried goods receipt or payroll run cannot double-post.
  • Maker–checker enforced. Tests confirm a PO requester cannot self-approve and a payroll drafter cannot approve their own run.
  • Concurrency taken seriously. lockForUpdate() on installments, purchase orders, stock movements, book loans, and refresh tokens.
  • Reversal over mutation. Posted entries are never edited; correction happens through generated reversal batches that preserve the audit trail.
  • 314 tests including 35 dedicated security tests across IDOR, MFA, token refresh, webhooks, and bypass regressions.

What costs it

  • A legacy single-sided entry path survives on the same route as the validated one.
  • Two different definitions of “period is locked” coexist in two services.
  • Reference numbers are generated by counting rows — a race under concurrency.
  • Business-rule failures thrown as bare \Exception, mapped to HTTP status only by the caller that happens to catch them.
  • 2803 any warnings mean the front end's type safety is thinner than tsc's clean exit suggests.
LOG-1

The journal endpoint accepts a single-sided entry, permanently unbalancing the ledger

Critical

app/Http/Controllers/Api/AccountingController.php:38 → app/Services/JournalService.php:66

storeJournalEntry branches on whether the request contains a lines key. With lines, it routes to JournalBatchService, which correctly enforces balance. Without lines, it falls through to the legacy JournalService::createEntry, which writes one debit or one credit with no offsetting side and no balance check at all.

Both paths sit behind the same perm:finance.journal.create gate, so any user who can create a legitimate balanced batch can also create an unbalanced one — by omitting a field. I confirmed this against a fresh database:

Probe — POST /api/accounting/journal-batches without a lines key

[PROBE 1] status=201 body={"description":"Unbalanced probe","type":"debit",
          "account_code":"1000","amount":"5000.00","reference_no":"JE-2026-0001"...}
[PROBE 1] ledger debits=5000 credits=0

The trial balance is now wrong by 5,000 with no error raised anywhere. Because posted entries cannot be edited, the only remedy is a compensating reversal — assuming someone notices. Fix: require lines on the batch route and retire the legacy single-entry path, or make createEntry demand a counterpart account.

LOG-2

An audited financial period still accepts new manual entries

High

app/Services/JournalService.php:52 vs. app/Services/LedgerService.php:213

Two services disagree on what a locked period means. LedgerService::assertPeriodOpen blocks ['closed', 'audited']. JournalService::createEntry checks only status === 'closed'. A period that has been through audit — the strongest lock the system offers — therefore remains writable through the manual path.

Probe — manual entry into a period marked audited

[PROBE 2] status=201 body={"description":"Post into audited period",
          "amount":"123.45","reference_no":"JE-2026-0001"...}

Post-audit mutation of a closed book is exactly the scenario financial controls exist to prevent. Fix: extract one shared period-lock guard and call it from both services.

LOG-3

Reference numbers are generated by row count, racing under concurrency

Medium

app/Services/JournalService.php:59

$count = JournalEntry::withTrashed()->whereYear(...)->count() + 1 reads then writes with no transaction and no lock, while reference_no carries a unique constraint. Two accountants posting in the same second both compute JE-2026-0001; one succeeds, the other gets an unhandled integrity violation surfaced as a 500. The count also scans the full year's entries on every single insert, so it degrades as the ledger grows. Fix: a database sequence or a locked per-year counter row.

LOG-4

Balance is validated before non-positive lines are filtered out

Low

app/Services/LedgerService.php:117-141

postBalanced sums all lines to check debits equal credits, then persists only lines where amount_cents > 0. A payload containing a negative line can satisfy the check and still write an unbalanced batch. No current caller passes negative values, so this is latent rather than live — but the guard should filter first, then validate.

Section 03 · 7.5 / 10

Interface

The front end is a 98-page React 19 SPA on Radix primitives with Tailwind 4. It is consistent, genuinely bilingual, and handles the unglamorous states that distinguish finished software from a demo.

What earns the score

  • Loading states in 91 of 98 pages, empty states in 79. That ratio is rare and it is what makes an app feel finished.
  • Real RTL, not a stylesheet flip. document.documentElement.dir switches with locale, and layouts carry rtl: variants down to calendar chevron rotation.
  • Radix under everything — dialogs, menus, and comboboxes inherit correct focus trapping, roles, and keyboard behaviour rather than reimplementing them.
  • Route-level code splitting across every portal, plus an ErrorBoundary and a forced-password-change gate in RoleGuard.
  • Seven roles, seven coherent portals — student, parent, teacher, admin, finance, HR, warehouse — sharing one shell and visual language.

What costs it

  • Only 26 of 171 component files carry explicit aria- attributes; custom widgets outside Radix lean on defaults.
  • 2803 any warnings concentrate at the API boundary — the layer where a shape change silently becomes a runtime crash.
  • src/lib/api.ts is a single 52 KB module; it should be split per domain.
  • RoleGuard redirects inside useEffect and renders null first, producing a blank frame before navigation.
  • No visible skeleton convention — loading is mostly spinners, which read as slower than they are.
UI-1

Runtime dependencies are declared as devDependencies

Low

school-web/package.json

React, Radix, TanStack Query, Recharts and the rest sit in devDependencies; only i18next and react-i18next are runtime deps. Vite bundles at build time so this works today, but npm ci --omit=dev produces a broken build, and the manifest misrepresents what the app actually needs. Cosmetic in effect, but it is the kind of thing that breaks a CI runner at the worst moment.

PERF-1

Tenant resolution runs an uncached joined query on every authenticated request

Medium

app/Services/SchoolContext.php:14

forUser() joins school_user_roles to schools with date-range predicates and runs from ResolveSchoolContext middleware on every single request. Several controllers then call it again inside the same request. This is a small fixed tax on all traffic that a short-lived per-request memo or cache would remove entirely.

PERF-2

PDF and report generation runs synchronously on web workers

Medium

routes/api.php — report-card, receipt, trial-balance, income-statement, inventory PDFs

Nine PDF endpoints render inline on the request thread. A class of parents opening report cards at the same time occupies PHP-FPM workers for the full render duration, starving ordinary requests. With no rate limit in front of them (SEC-1), this is also the cheapest way to take the API down. Fix: queue the render, return a job handle, deliver via signed URL.

Worth noting on the positive side: dashboardKpis wraps everything in Cache::remember with a school-scoped key and computes the attendance rate in a single selectRaw aggregate rather than iterating records. Student CSV import streams with a per-row transaction and size caps. These are the choices of someone who has been burned before.

Section 05 · 8.0 / 10

Security

The strongest dimension, and by a wide margin the part of this codebase I would most readily defend to a reviewer. The authentication design in particular is better than what most production SaaS ships.

What earns the score

  • Refresh-token rotation with reuse detection. Tokens carry a family ID; presenting a rotated token revokes the entire family under a row lock. This is the OAuth BCP design, implemented correctly.
  • Browser credentials never touch JavaScript. Access and refresh tokens are encrypted into path-scoped httpOnly cookies; the SPA receives identity data only.
  • Timing-safe login. A hash check runs even for non-existent users, so response time does not disclose whether an email is registered.
  • Layered authorisation. Coarse role: gates plus ~90 granular perm: gates, so a warehouse user can receive goods but never approve them.
  • Webhooks done properly — Stripe signature verification, an idempotency table, payload-hash comparison against the stored event, and lockForUpdate claiming.
  • MFA with enrolment, challenge, recovery codes, and an approval-gated help-desk reset path.
  • Immutable tenancy on write. An updating hook re-stamps school_id from server context, so a client cannot move a record between schools even via forceFill.
  • CSP without unsafe-inline on scripts, HSTS, frame-ancestors none, and a preflight script that refuses to deploy with debug on, HTTP URLs, or placeholder secrets.

What costs it

  • No rate limit anywhere on the authenticated API surface.
  • Tenant isolation is fail-open, not fail-closed, whenever context is absent.
  • A deliberate cross-tenant read of legacy null-school rows in the journal list.
  • Eight dependency advisories outstanding as of today.
  • connect-src https: in the CSP permits exfiltration to any HTTPS host.
SEC-1

The entire authenticated API has no rate limiting

Critical

routes/api.php · bootstrap/app.php

Throttles exist on login, password reset, refresh, MFA, and the payment webhook — and nowhere else. Laravel 12 does not apply throttle:api by default, and this application never registers it. Every authenticated endpoint is unmetered, including the expensive ones:

Unthrottled and expensive

routes/api.php:108  GET  /student/report-card/pdf
routes/api.php:154  GET  /teacher/grades/export
routes/api.php:180  POST /admin/users/import-students
routes/api.php:393  GET  /accounting/reports/trial-balance/pdf
routes/api.php:426  GET  /warehouse/reports/consumption/pdf
    grep -c throttle routes/api.php → 10  (all on auth + webhook)

Any authenticated account — a student's, a leaked token, a compromised parent login — can loop a PDF endpoint and exhaust PHP-FPM workers. This is simultaneously the top security and top availability finding. Fix: a global throttle:api baseline plus tighter per-route limits on exports, imports, and PDFs.

SEC-2

Tenant isolation is fail-open when no school context is set

High

app/Providers/AppServiceProvider.php:37-41

The global scope reads if ($currentSchool->has()) { $query->where(...) }. When context is absent, no predicate is applied and the query returns every tenant's rows. I confirmed the behaviour directly:

Probe — same model, with and without tenant context

[PROBE 3] rows visible inside school-A context = 1
[PROBE 3] rows visible with NO context        = 2  [Cat A, Cat B]
[PROBE 3] => FAIL-OPEN: unscoped read returned EVERY school's rows

In practice this is mitigated — all HTTP routes carry school.context, and console commands wrap work in CurrentSchool::run(). But the safety property depends on every future queue job, command, and webhook remembering to opt in, and the public webhook route is already outside the middleware group. A missing wrapper produces silent cross-tenant disclosure with no error. Fix: throw on unscoped access and require an explicit withoutGlobalScope opt-out at each legitimate site.

SEC-3

Journal batch listing deliberately returns rows belonging to no school

Medium

app/Http/Controllers/Api/AccountingController.php:54-55

indexJournalBatches matches the caller's school orWhere(school_id IS NULL). Every school sees the same legacy null-school batches. The isolation migration made school_id non-null, so this should now match nothing — but it is a cross-tenant read left deliberately in place, and it will silently start leaking again if any path ever writes a null-school batch.

SEC-5

Two small hardening gaps in headers and proxy trust

Low

app/Http/Middleware/SecurityHeaders.php:29 · bootstrap/app.php:52

The CSP sets connect-src 'self' https:, which permits an injected script to reach any HTTPS host — worth narrowing to the known API origin. Separately, trustProxies lists '*.fly.dev' alongside CIDR ranges, but that setting expects IPs or CIDRs; the hostname entry never matches and is dead configuration.

Section 06 · 5.5 / 10

Availability

The weakest dimension and the one that most limits what this application can responsibly be sold as. Backup and restore are handled with real rigour; almost everything else assumes one machine that does not fail.

What earns the score

  • Backup is genuinely well done — daily Postgres dump with SHA-256, a per-table row-count manifest, an uploads archive, and a rehearsed restore verified in 9.85 s. Most teams never test restore at all.
  • Work is separated by concern — two API replicas, a dedicated queue worker, and a scheduler, each independently restartable.
  • Transactional outbox with retry and dead-lettering, drained every minute with withoutOverlapping.
  • Documented rollback that correctly warns against using migrate:rollback to undo tenancy columns once multi-school data exists.
  • restart: unless-stopped everywhere; health checks on Postgres and Redis.

What costs it

  • The only health endpoint a monitor can reach tells it nothing.
  • No container health checks on nginx, either API replica, the queue, or the scheduler.
  • Single Postgres, single Redis, single host — three independent single points of failure.
  • Webhook events can wedge in processing and are never reclaimed.
  • No rate limiting, so a single client can exhaust the worker pool (SEC-1).
  • CI workflows are deleted from the working tree.
AVL-1

The public health probe cannot detect an unhealthy application

High

routes/api.php:32 · app/Http/Controllers/Api/HealthController.php

There are two health endpoints and neither is usable for its purpose. /api/healthz is public but returns a hardcoded {"status":"ok"} — it stays green with the database down. The real dependency check, /api/health, sits behind role:admin, so no load balancer, uptime monitor, or orchestrator can call it.

The practical consequence: a replica whose database connection has failed keeps passing checks and keeps receiving traffic. Fix: expose an unauthenticated liveness/readiness probe that checks database and cache reachability without disclosing versions or internals.

AVL-2

No container health checks on the application tier

High

laravel-api/docker-compose.prod.yml

Postgres and Redis define healthcheck blocks. nginx, api1, api2, queue, and scheduler do not. Nothing detects a PHP-FPM process that is alive but wedged, so nginx keeps routing to it and half of all requests fail while the stack reports healthy. A silently dead queue worker is worse — notifications and outbox events simply stop, with no alert.

AVL-3

Webhook events can wedge in processing and are silently lost

High

app/Services/PaymentGatewayService.php:326-329

An event is claimed by setting status = 'processing'. If the worker dies mid-handler, the row stays in that state forever. On Stripe's retry, the claim check finds processing and returns ['success' => true, 'already_processed' => true] — a 200, which tells Stripe to stop retrying. A payment that was never actually applied is now permanently dropped, with the provider believing it was delivered. Fix: treat processing rows older than a timeout as reclaimable, or return 5xx so the retry is preserved.

AVL-4

Single-host topology with three single points of failure

Medium

laravel-api/docker-compose.prod.yml

Two API replicas provide process redundancy, not availability — they share one host, one Postgres with no replica or failover, and one Redis holding cache, sessions, and queues. Any of the three failing takes the whole system down, and recovery means restoring from the nightly dump. That is a recovery point of up to 24 hours.

This is a legitimate architecture for a single school with a maintenance window. It is not one for a multi-tenant product sold to several schools, which is what the tenancy work throughout the codebase is clearly building toward. The gap between the isolation model's ambition and the deployment topology's capability is the single largest inconsistency in this project.

AVL-5

CI workflows are deleted from the working tree

Medium

.github/workflows/ci.yml and deploy-frontend.yml are tracked in git but absent from disk, along with the school-mobile app (56 files) and several audit documents. Whatever the reason, the effect today is that no automated gate runs on push — which is how eight dependency advisories accumulated unnoticed (SEC-4). Restore them before the next deployment.

Section 07

What to fix, in order

Ordered by risk-to-effort. The first four are days of work and would move the overall rating to roughly 8.5.

  • Now Close the unbalanced-ledger path (LOG-1)Require lines on the journal batch route and retire JournalService::createEntry. This is a financial-integrity defect in an accounting system — it outranks everything else here.
  • Now Add a global API throttle (SEC-1)One line of middleware configuration closes the top security finding and the cheapest denial-of-service vector simultaneously. Follow with tighter limits on PDF, export, and import routes.
  • Now Expose a real health probe and add container health checks (AVL-1, AVL-2)Without these, the redundancy already paid for does not function — traffic keeps flowing to dead workers.
  • Now Reclaim stuck webhook events (AVL-3)Add a staleness timeout to the processing claim. Silently dropped payments are the most expensive class of bug in this system.
  • Next Unify the period lock and fix reference generation (LOG-2, LOG-3)One shared guard for closed and audited periods; a sequence or locked counter instead of count() + 1.
  • Next Make tenant scoping fail-closed (SEC-2)Throw on unscoped access with an explicit opt-out at each legitimate call site, so the guarantee holds by construction rather than by discipline.
  • Next Restore CI and add a scheduled dependency audit (AVL-5, SEC-4)Then clear the eight outstanding advisories.
  • Soon Move PDF rendering to the queue (PERF-2)Return a job handle and deliver via signed URL. Removes the worker-starvation risk permanently.
  • Soon Managed Postgres with replication and PITR (AVL-4)The prerequisite for selling this to more than one school. Nightly dumps are a 24-hour recovery point.
  • Soon Type the API boundary and split api.ts (UI-1)Retire any in the request/response layer first — that is where the 2803 warnings actually cost something.

Section 08

Closing assessment

Judged as engineering, this is well above the median for its category. Refresh-token rotation with family revocation, encrypted httpOnly credential cookies, idempotent ledger postings, maker–checker approval chains, and a rehearsed restore are not things most school management systems have. The comments in the code explain why rather than what, the tests cover adversarial cases rather than happy paths, and someone clearly thought hard about multi-tenancy before writing the migration.

The pattern in the defects is consistent and worth naming: the new code is careful, and the old code it replaced is still reachable. JournalBatchService enforces balance while JournalService does not, and both answer the same route. LedgerService respects audited periods while JournalService does not. Legacy HR and finance endpoints keep coarse role gates while their replacements use granular permissions. Each hardening pass added a correct implementation without removing the incorrect one, and the security of the whole is set by the weakest path an attacker can still reach — not the best one.

The second pattern is the gap between ambition and operations. The tenancy work is designed for many schools; the deployment is designed for one host. Closing that gap is an infrastructure decision, not a code one, and it should be made deliberately rather than discovered during an outage.

Verdict: 7.0 / 10. Suitable for production at a single school with a maintenance window, once the four Now items are closed. For multi-school SaaS, the availability work in Section 06 is a prerequisite, not an optimisation.
